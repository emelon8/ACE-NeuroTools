# Add a community reader or analysis module through a documented extension contract

GitHub: https://github.com/emelon8/experiment_analysis/issues/83

## Parent

https://github.com/emelon8/experiment_analysis/issues/69

## Status and source

**Planning draft — human decisions required.** Suggested ownership role: Extension API owner; no person is assigned. Proposed stage: Community.

Project brief: modular, community-first development; the meeting supports community participation.

## What to build

Prove extensibility with one reference module that declares its inputs, settings, checks, execution, and outputs and becomes usable in both GUI and CLI without modifying either interface.

## Acceptance criteria

- [ ] Document a versioned contract covering identity/version, compatible inputs/outputs, parameter descriptions/units, preflight, progress/errors, and provenance.
- [ ] A contributor installs/enables one example module through the agreed mechanism and uses it end to end from GUI and CLI.
- [ ] Compatibility errors and module failures are visible without being misreported as successful scientific work.
- [ ] Runs pin and report module versions; disabling/upgrading a module does not silently rewrite past runs.
- [ ] Tests verify the public contract with fixtures; the trust/distribution policy is explicit and does not claim unimplemented isolation.

## Ownership and overlap

Start from existing reader registries and analysis selection patterns. Defer remote marketplaces, automatic installation, and arbitrary executable plugins until explicitly scoped.

Claim this issue and link the active PR before coding. Shared behavior belongs in the common application layer, with GUI/CLI equivalence checked through observable behavior. Demonstrate the acceptance criteria to a human reviewer before closure.
