## Decision to make

What is the authoritative saved experiment configuration, and what happens to existing CSV/JSON workflows?

**Status: decided 2026-09-16 by Elijah Keldsen (decision owner) — see the decision record at the bottom of this file and the recording comment on [#91](https://github.com/emelon8/experiment_analysis/issues/91).**

**Suggested participants:** Application maintainer + existing CLI users. No person is assigned. **Resolve:** First.

## Context

Area: Persistence. This topic comes from the Comenius planning synthesis of the supplied meeting and project brief. See the [decision register](https://github.com/emelon8/experiment_analysis/blob/proj-comenius/docs/comenius/decisions.md#d05) for the shared snapshot.

## Options

1. CSV remains authoritative.
2. versioned manifest with CSV import/export.
3. database with explicit export/migration.

## Recommendation

Define a versioned, inspectable configuration contract, with explicit defaults/override precedence and non-destructive CSV/JSON import. Decide export coverage rather than promising lossless round-trip of unknown fields.

## Trade-offs and questions to resolve

Reject conflicting identifiers and report unsupported fields. GUI and CLI must resolve the same effective settings. Migration should preserve the originals and a mapping to prior IDs.

**Decision record:**

- Chosen option: **Option 2 — versioned manifest with CSV import/export**, made
  concrete as: the authoritative saved configuration is a set of small
  **canonical JSON documents** (sorted keys, fixed indent), one document per
  concern (experiment identity, one per analysis type), stored in the
  experiment's `parameters/` directory, validated by versioned **JSON Schema**
  files, and tracked by experiment version control (EVC). All editing goes
  through the GUI (schema-driven forms) or the machine-mode CLI for agents;
  CSVs become a **non-destructive import path** (first extract is recorded as
  the "imported from CSV" root revision) plus a **compatibility writeback**
  that keeps existing CSV-reading pipelines working during migration, then an
  export-on-demand format.
- Rationale: JSON gives per-parameter key-level diffs in EVC (the researcher
  question is "which parameter changed"); JSON Schema drives both GUI form
  generation and backend validation from one definition; JSON sidecars are the
  neuroscience community's standardization answer (BIDS, incl. BEP032 animal
  ephys and Microscopy-BIDS vocabularies); the format is pure standard
  library. Unknown lab-specific CSV columns are preserved verbatim in an
  explicit passthrough section rather than promising lossless typed round-trip
  of unknown fields (per this file's original recommendation).
- Important rejected alternatives: CSV-authoritative (Option 1 — the source of
  the config-disagreement and template-mismatch bug class; non-standard);
  YAML/TOML (their human-hand-editing advantage is moot in a GUI-first design;
  YAML parsing ambiguity, TOML stdlib write gap); SQLite/HDF5/NWB as the
  editable store (binary blobs destroy key-level diffing — NWB remains a data
  export target, not the parameter store); server database (Option 3 —
  operational burden, conflicts with "files inside the experiment").
- Human owner / consulted participants: Elijah Keldsen (owner). Consulted:
  Claude decision brief with open-source verification (BIDS/BEP032, DVC
  pointer files, python-neo IO detection, react-jsonschema-form/JSONForms,
  VS Code settings-over-file model), 2026-09-16 session.
- Date and evidence: 2026-09-16. Evidence: `docs/design/evc-implementation-plan.md`
  §Phase 4, ADR `docs/adr/0002-json-parameter-documents.md`, working
  implementation slice `aceneurotools.evc.csv_bridge` + schemas under
  `src/aceneurotools/evc/schemas/`.
- Affected implementation changes: unblocks EVC Phase 4 (`csv_bridge`);
  fixes audit bug 4 (experiments.csv template mismatch) as a precondition;
  sets direction for F03 (GUI settings editing) and F01; interacts with
  D02/D03/D06/D09/D10, which remain open.
