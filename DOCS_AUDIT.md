# Documentation audit

Audited on 2026-09-15 on branch `docs-accessibility-audit`. This review covers the current working tree, including documentation and packaging edits that were already uncommitted when the branch was created. It covers `README.md`, the MkDocs pages, the three short package READMEs, and the single-AVI checklist. Claims were checked against the current Python code, templates, scripts, workflows, and repository files. The audit did not verify the live Read the Docs site or run a full scientific analysis.

## Overall assessment

The documentation has a useful structure and names the main workflows, but it is not yet a reliable guide for a reader who does not program. The primary path from installation to a first successful analysis relies on Git, a terminal, CSV editing, and Python concepts without explaining them. Several examples suggest a full analysis while the shown arguments only load or preprocess data. Accuracy problems in the setup and modality guides can lead to failed runs or wrong expectations about results.

## Readability and coverage gaps

- **Start with the reader's task.** The README and documentation home open with “object-oriented Python library,” a class diagram, CNMF-E, EEG/LFP, and multimodal terminology. A short plain-language overview should say what files a lab starts with, what the tool does to them, and what files or plots it produces. Define *miniscope*, *calcium imaging*, *electrophysiology*, *channel*, *TTL pulse*, *CNMF-E*, and *headless* when first used.
- **Give a true first-run path.** The current getting-started guide uses placeholder paths and line numbers 96/97, but supplies no complete example row or tiny permitted dataset and no description of a successful run. A non-programmer needs a concrete example with “before” folders, the command to copy, expected messages, output location, approximate runtime/storage, and a way to check the result.
- **Explain prerequisites before commands.** “Clone,” “editable mode,” “project_path,” “kwargs,” “module CLI,” and “Python API” appear before they are explained. Give a short terminal setup path (including how to get Git and micromamba), say which commands to paste versus which values to replace, and choose the command-line workflow as the primary path for non-programmers. Keep Python snippets in an advanced section.
- **Separate user help from maintainer material.** Deployment, releasing, API stubs, and the class diagram are useful to developers, but dominate navigation and the README. Label those sections for maintainers and put the experiment workflow, data preparation, and result interpretation first.
- **Clarify output handling.** [guides/data_management.md](docs/guides/data_management.md) says outputs are saved adjacent to raw recordings; [guides/miniscope.md](docs/guides/miniscope.md) names `saved_movies/`, but there is no consolidated output map or explanation of which products are generated under which flags. Add an output table and note that derived files may appear inside the raw-data directory.
- **Use consistent names and formatting.** Prefer “electrophysiology” over “electrophysical,” a consistent capitalization for miniscope/ephys, and one form for the `line number` identifier. Replace GitHub admonition syntax (`> [!IMPORTANT]`) in the MkDocs guide with the MkDocs admonition form used elsewhere so the notice renders predictably.

## Verification and limits

Static checks found one missing local heading anchor and no missing local Markdown link targets. The README fixture claim was checked against the repository tree. Pipeline and CSV behavior was checked against function signatures and relevant loaders. `mkdocs` is not on the current shell PATH, so this audit did not render the site. The live hosted URL and Box authentication procedure should be validated in a real environment before promising them to readers.
